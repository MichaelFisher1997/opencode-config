Deliver the current repository's work end to end. Execute this workflow rather than merely proposing commands.

User options and context: $ARGUMENTS

Optional arguments are natural-language instructions or `base=<branch>`, `branch=<new-branch>`, and `remote=<push-remote>`. Interpret them as input, never as shell code. With no arguments, discover sensible repository-specific defaults.

If the first argument is the standalone word `merge` (for example, `/ship merge` or `/ship merge base=dev`), enable merge mode. This is explicit authorization to merge this workflow's PR/MR after the checks below pass, without asking for another confirmation. Record this mode in the progress checkpoint and preserve it across resumes. A branch name or contextual mention containing "merge" does not enable it. Plain `/ship` stops at readiness as before.

Invoking this command authorizes integrating the target branch, resolving conflicts, creating a feature branch, committing all current staged/unstaged changes and non-ignored untracked project files, pushing, opening a PR/MR, and babysitting it with focused follow-up fixes. Existing local commits are included too. Respect explicit exclusions, repository instructions, and higher-priority permissions. Inspect and explicitly stage reviewed paths; do not blindly stage everything, include secrets or incidental local artifacts, or discard existing work. Ask with the question tool only for genuine ambiguity or blockers.

## 1. Discover conventions and destination

1. Create a todo list. Load the `baby-sit` skill now to establish its boundaries and later monitoring requirements. Load `github` for GitHub repositories and any other installed skill directly relevant to this repository's delivery workflow. Read the baby-sit host-specific reference.
2. Read repository instructions, contributing guidance, branch/commit naming rules, PR/MR templates, and validation commands. Inspect status including untracked files, staged and unstaged diffs, `git log --oneline -10`, branches, remotes, tracking, and existing requests. Detect unfinished merge/rebase/cherry-pick operations; resolve their ownership before starting another operation.
3. Identify the target repository and fetch remote refs. Identify the writable source/push remote separately, including fork setups; do not assume `origin` is the upstream repository. Verify host CLI authentication without exposing credentials. Use `gh` for GitHub and the baby-sit GitLab reference for GitLab. Report a blocker for an unsupported host rather than assuming GitHub.
4. Determine the PR/MR **base/target** branch in this order: explicit user option, an existing matching request's target when resuming, an explicit repository contribution/integration-branch rule, then the target repository's live default branch from host metadata. On GitHub, query the verified target repository with `gh repo view --json defaultBranchRef`; a live remote HEAD lookup is a fallback. Verify the selected branch exists remotely. Do not guess from names such as main, master, dev, or develop, use stale cached remote HEAD alone, or confuse the current source HEAD with the target. Ask if evidence conflicts or remains ambiguous.
5. Inspect all commits and the total diff that would enter the request. Include current work by default as authorized above; flag unexpected inherited branch history before publishing it. Detect an existing matching open PR/MR to avoid duplicates. When resuming this workflow, reuse its source branch and request unless the user explicitly requests a replacement. Do not reopen a closed request automatically.

## 2. Create the branch and update from the target

1. For a new delivery, choose a descriptive new source branch from the actual changes, following documented conventions and recent branch names (including issue IDs when required). Honor an explicit branch name if valid. If no convention exists, use a short kebab-case topic with an appropriate prefix such as `fix/`, `feat/`, or `chore/`. Validate with `git check-ref-format --branch` and check local and remote collisions; choose a unique name rather than overwriting a branch. Create it from the current HEAD to retain local commits, and carry the working tree changes with it. Never commit or push directly onto the target branch.
2. Integrate the latest fetched target into this source branch using a merge by default, preserving existing history. Also reconcile a resumed source branch with its remote if it advanced. Do not use an unqualified pull that might update the wrong tracking branch. If repository policy requires rebasing, use it only for unpublished local commits; ask if satisfying that policy would require rewriting published history.
3. Preserve dirty work before integration when necessary: record the original status and staged/unstaged state, stash tracked changes and non-ignored untracked files with an identifiable label, and record the exact stash object. Restore that exact stash after integration using `git stash apply --index` where feasible. Keep the recovery stash until restoration and verification succeed; do not drop it without any required deletion approval. Never use reset/clean or overwrite files to get a clean tree. Report a retained recovery stash in the handoff.
4. Resolve both upstream merge conflicts and any restored-work conflicts by reading both sides and preserving the intended behavior. Do not blanket-select ours/theirs. Stage resolved paths, complete the operation, and verify there are no unmerged entries or introduced conflict markers. Ask only when a resolution requires an unknown product decision or risks losing work. Track recovery details if blocked mid-operation.

## 3. Validate, commit, push, and open the request

1. Review the integrated result and entire source-to-target diff, including every included commit. Run applicable tests, lint, and type checks according to repository instructions; use Bun for JavaScript package commands where applicable. Fix in-scope failures and rerun affected checks. Report unavailable checks honestly.
2. Before each commit inspect status, unstaged diff, staged diff, and `git log --oneline -10`. Explicitly stage all reviewed project changes covered by this invocation, including intended deletions and new files. Inspect the final staged diff for omissions, unintended files, and secrets. Follow repository commit-message style and hooks; split coherent commits when useful. Do not create empty commits. Hook failures require fixes and a new commit attempt, not hook bypasses or an amend.
3. Push the source branch to the verified writable remote and set its upstream. Reconcile concurrent remote updates safely; do not force-push. If the resulting branch has no changes relative to the target, report that there is nothing to propose and do not create an empty request.
4. Create the PR/MR against the explicitly selected target repository and base branch, with the correct source owner/branch for forks. Follow the template and title conventions, summarizing changes, validation, and limitations. Reuse a matching request when resuming and preserve user-authored text and draft status. On GitHub use `gh pr create` with explicit repository, base, and head values.
5. Return the URL in progress. When T3 linking tools are available, register the PR immediately and verify it remains linked before finishing.

## 4. Enact baby-sit through completion

Continue immediately using the loaded `baby-sit` skill's observation, repair, automated-review, security, persistence, and completion procedures. Publishing the request is an intermediate step, not completion.

Carry forward the repository, source/push remote, target branch, request URL, current head SHA, local validation, and any recovery stash. Observe CI and known automated reviewers, evaluate actionable findings, make focused repairs, commit and push, and recheck the latest head. Apply the skill's default monitoring budget, retry limits, and quiet period unless the user supplied overrides; retain counters across repairs and resumes.

Only merge when merge mode is enabled and section 5 is satisfied. Do not enable auto-merge ahead of completed babysitting, rewrite published history, bypass hooks/protections, or change CI/security policy merely to pass. Do not claim background monitoring without a real supported scheduler.

For plain `/ship`, finish with the skill's **Ready**, **Blocked**, or **Budget exhausted** report. In merge mode, continue to section 5 after readiness; readiness alone is not completion. Include the request URL, source and target branches, verified SHA, checks/reviews/security results, remaining limitations, and the next action if needed. Mention any work excluded from publication or retained recovery stash. If no request was needed because there was no diff, report that explicitly instead of claiming a validated PR.

## 5. Merge when requested

1. Merge mode supplies the explicit merge authorization required by `baby-sit`; its default automatic-merge-off rule still applies to plain `/ship`. Complete its checks, review/security evaluation, and quiet period first. Require all applicable checks to pass, with only verified legitimate skipped/not-applicable results accepted; do not merge with failed optional checks, pending or missing expected automation, or unresolved actionable findings. If a new project genuinely has no configured automation, confirm that from configuration and host activity, run applicable local validation, and disclose the absence rather than treating an empty checks list as green.
2. Immediately before merging, refresh the request state, exact head SHA, target branch, checks, reviews, unresolved discussions, draft status, mergeability, and the authenticated user's merge permissions. Required human approvals must be satisfied as well. A draft, permission denial, unknown mergeability, or unmet repository requirement blocks merging. Do not self-approve, use administrator overrides, or relax repository rules. If the head or relevant base state changed, revalidate and resume babysitting within the original budget before attempting a merge.
3. Choose the merge method from repository instructions and allowed methods. If no preference is documented, prefer squash when allowed, otherwise a merge commit, otherwise the allowed rebase-merge method. This host-side merge method does not authorize rewriting the published source branch. Follow repository conventions for the resulting commit title/body.
4. On GitHub, use `gh pr merge` with the explicit request and repository, the selected method, and `--match-head-commit` set to the exact validated head SHA. Never use `--admin` or `--delete-branch`. For a required merge queue, use the normal queue-aware operation without bypassing the queue; continue observing its checks and final state. On GitLab, use its documented merge operation with the equivalent expected-head SHA guard and repository policy. Do not retry a head mismatch without revalidating the new head.
5. Verify the remote request actually reports merged and obtain its merge commit SHA and merge time. A successful CLI exit or queue admission alone is not proof of a merge. Continue queue monitoring within the remaining budget; if it expires, report **Budget exhausted**, the exact queue/auto-merge state, and whether the host may still merge later. If permissions or rules prevent merging, report **Blocked** with the specific missing requirement, preserving the ready PR for the user.
6. After a verified merge performed by this workflow, report **Merged** with the URL, target branch, validated source SHA, merge SHA/time, and validation summary. This is the merge-mode completion outcome instead of the skill's pre-merge **Ready** outcome. If someone else closes or merges it before this workflow acts, follow the skill's external-state reporting and do not claim to have merged it. Do not delete branches or recovery stashes without separate authorization.
